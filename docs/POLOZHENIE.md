# Положение о рейтинге: как оно реализовано

Документ: «Положение о системе рейтинга и поощрения студентов Путь героя»,
редакция **2.0** от 12 октября 2026 года, АНО ПО «ИТ Хаб Нальчик».

Положение главнее любых других правил в проекте. Тарифы и границы живут
в одном месте — [`hero_path/settings/polozhenie.py`](../hero_path/settings/polozhenie.py);
каждая величина там снабжена номером пункта. Если тариф продублирован где-то
ещё, убирается дубликат, а не правится.

Первая дата начислений — **19 октября 2026**. Недели до неё не оплачиваются.

## Недельный расчёт (раздел 3)

```
Б = 17 × К / 100 + 13 × П / 100
```

* **К** — средний процент актуальных КТ семестра. Несданная актуальная КТ
  считается как 0% (п. 3.1). Будущие КТ исключаются.
* **П** — процент посещаемости недели: посещённые пары, делённые на
  проведённые (п. 3.2). Отметка об участии онлайн — это присутствие.

**13 баллов в неделю — это всё, что даёт посещаемость.** Других источников
рейтинга за присутствие нет: бонусы за серии без пропусков и без опозданий
начисляются монетами, иначе неделя без пропусков приносила бы 13 + 5 и
выходила за тариф. Настройка `ATTENDANCE_FULL_WEEK` (15 баллов за полную
неделю) удалена — в коде она не использовалась, но обещала ровно то, что
пункт 3.4 ограничивает.

Студент получает **Б рейтинговых баллов и Б монет**. Максимум недели — 30.

Две части считаются независимо. Нет данных по одной — её расчёт
откладывается и выплачивается, когда данные придут (п. 3.6). Отсутствие
данных нулём не считается и нарушением не является.

### Актуальность КТ

Поля «актуальна» в выгрузке LXP нет, поэтому актуальность выводится из
статуса темы. Статусы, которые реально приходят (снимок 12.10.2026,
574 студента, 131 833 темы):

| Статус | Доля | Трактовка | Почему |
|---|---|---|---|
| `NOT_PASSED_YET` | 91,6% | будущая, не в расчёте | тема есть в программе, но студент до неё не дошёл |
| `PASSED` | 3,0% | сдана, 100% | |
| `MASTERED` | 0,6% | сдана, 100% | «освоена» — это сдано |
| `IN_REVIEW` | 2,4% | на проверке, не в расчёте | студент сдал, решения преподавателя ещё нет |
| `IN_PROGRESS` | 0,9% | актуальная, 0% | |
| `FAILED` | 0,3% | актуальная, 0% | |
| `FOR_REVISION`, `FOR_REWORK` | 0,1% | актуальная, 0% | работа вернулась на доработку |
| `NOT_MASTERED` | 0,03% | актуальная, 0% | |
| пусто | 1,1% | не в расчёте | это отсутствие данных, а не несданная тема |

Отсюда два решения, каждое из которых меняет деньги студентов.

**`NOT_PASSED_YET` исключается.** Иначе актуальными становятся все темы
программы за четыре года: успеваемость каждого падает до 3%, и недельное
начисление обнуляется для всей группы.

**`IN_REVIEW` исключается, а не считается несданной.** Это треть тем, с
которыми студент что-то делал. Считать их нулём значит отнимать баллы за то,
что преподаватель не успел проверить, — тот же принцип, что в п. 3.6:
решения нет, расчёт по этой теме отложен. Накрутить это нельзя: отклонённая
работа возвращается как `FOR_REVISION` и уже считается несданной.
Если колледж решит иначе, достаточно очистить
`POLOZHENIE_PENDING_TOPIC_MARKERS` — тогда `IN_REVIEW` пойдёт в расчёт как
0%, и успеваемость в среднем по снимку падает с 73% до 49%.

### Открытый вопрос: что считать актуальной КТ

Проба на пилотной группе показала, что действующее приближение негодно:
**14 студентов из 17 получили бы 100% и полные 17 баллов**. Разбивка
объясняет почему — LXP держит тему в `NOT_PASSED_YET` до первой сдачи,
поэтому у студента без возвращённых работ знаменатель равен числу сданных:

| Студент | сдано | не сдано | на проверке | будущих | К |
|---|---|---|---|---|---|
| Афаунов | 2 | 0 | 1 | 192 | 100% |
| Пшихачева | 39 | 0 | 4 | 152 | 100% |
| Тумов | 2 | 0 | 0 | 193 | 100% |
| Картлыков | 7 | 9 | 0 | 179 | 43,75% |

Пшихачева сдала 39 тем, Тумов — две, у обоих 100%. Различает студентов
только то, вернул ли преподаватель работу.

Четыре возможных правила и команда, которая считает все сразу:

```bash
dcp exec web python manage.py compare_ct_rules
```

1. **решённые** (действует сейчас) — актуальны темы с вынесенным решением.
   Даёт 100% почти всем.
2. **+ на проверке** — сданное на проверку считается несданным. Различает
   студентов, но наказывает за непроверенную работу и всё равно даёт 100%
   тем, у кого на проверке ничего нет.
3. **текущие дисциплины** — актуальны все темы дисциплин, по которым в этом
   семестре были занятия. Ближе всего к букве п. 3.1. Следствие: темы, до
   которых семестр не дошёл, считаются несданными, поэтому в начале
   семестра процент низкий у всех и растёт к сессии.
4. **к норме курса** — доля сданного от ожидаемого к этой дате. Не буква
   п. 3.1, зато прямо отвечает смыслу п. 3.4: оплачивается поддерживаемый
   темп.

Выбор за колледжем: это вопрос о том, что считать успеваемостью, а не
технический. Снять неопределённость полностью может только признак
текущего семестра в самой LXP — если он есть, нужно спросить владельца API.

> **Осторожно с подстроками.** Первый прогон на живых данных показал, что
> `NOT_PASSED_YET` читался как сданная тема: в строке есть подстрока
> `PASSED`. Это 120 801 запись из 131 833. Поэтому в `ct_status` отрицание
> (`NOT_`, `НЕ `) проверяется раньше маркеров закрытия и перебивает их.

**Список нужно сверять с живыми данными после любого изменения в LXP:**

```bash
dcp exec web python manage.py probe_topic_statuses
```

Команда печатает статусы, их трактовку и распределение итоговой
успеваемости по студентам. По распределению ошибку видно сразу: если у
большинства выходит 100% или, наоборот, ни у кого нет актуальных КТ —
маркеры разъехались с данными. Проверка обязательна перед первым
начислением и после каждого обновления LXP.

## Запуск расчёта

Автоматически: Celery, понедельник 05:00 — считается прошедшая неделя
(задача `accrue_polozhenie_week`). Расчёт идёт после ночной загрузки отметок
и снимка LXP, иначе последний учебный день недели потерялся бы.

Вручную:

```bash
# посмотреть расчёт, ничего не начисляя
dcp exec web python manage.py accrue_week --dry-run

# конкретная неделя
dcp exec web python manage.py accrue_week --week 2026-10-19

# добрать все недели с начала сезона
dcp exec web python manage.py accrue_week --since 2026-10-19
```

Повторный запуск безопасен: один период не оплачивается дважды (п. 2.4).

## Разовые начисления (разделы 5–7) и роли (раздел 4)

```bash
# все тарифы таблицами
dcp exec web python manage.py award_polozhenie --tariffs

# мероприятие: уровень и роль определяют тариф
dcp exec web python manage.py award_polozhenie event --user ivanov \
    --key hack-2026-10 --level region --role speaker --title "Хакатон КБР" --by kumykova

# олимпиада: победа после учтённого участия доплачивает разницу
dcp exec web python manage.py award_polozhenie olympiad --user ivanov \
    --key olymp-prog-2026 --level federal --role win --by kumykova

# проект: ключ задания, по нему не платим дважды
dcp exec web python manage.py award_polozhenie project --user ivanov \
    --key inc-42-stage-1 --role stage --by sarakhov
```

`--key` обязателен: по нему Положение запрещает платить дважды за одно и то
же. Для мероприятий и олимпиад применяется **одна наивысшая** подтверждённая
роль; если роль выше уже засчитанной, начисляется разница (п. 5.2, 6.3).

**Регулярные роли** заводятся в админке, раздел «Роли студентов»: вид роли,
дата начала и дата окончания. Начисление идёт каждую неделю вместе с учебным
и пропорционально числу учебных дней действия статуса (п. 4.2). Совмещённые
роли суммируются.

## Списания (раздел 9)

```bash
dcp exec web python manage.py award_polozhenie absence --user ivanov --day 2026-10-20 --by tutor
```

−1 за каждую пропущенную пару, не больше −4 за учебный день. Монеты не
списываются (п. 9.4).

**Автоматического ежедневного прогона у списаний нет, и это сделано
намеренно.** Пункт 9.2 запрещает применять штраф, пока причина выясняется,
а признака уважительной причины в данных LXP нет. Штраф применяется после
подтверждения тьютором.

## Каталоги магазина и нашивок

Товары и нашивки заводила только демо-команда, запрещённая в продакшене.
Прод-команда:

```bash
dcp exec web python manage.py sync_catalogs --dry-run
dcp exec web python manage.py sync_catalogs
# применить цены и награды из кода к уже существующим записям
dcp exec web python manage.py sync_catalogs --update-existing
```

Пользовательских данных не трогает. Снятые с продажи товары
деактивируются, а не удаляются: на них ссылаются прежние покупки.

## Статусы (раздел 8)

| Рейтинг | Статус |
|---|---|
| 0 ≤ Р < 100 | Новобранец |
| 100 ≤ Р < 250 | Стажёр |
| 250 ≤ Р < 500 | Специалист |
| 500 ≤ Р < 700 | Профи |
| 700 ≤ Р < 900 | Мастер |
| Р ≥ 900 | Легенда |

Источник границ — `POLOZHENIE_STATUSES`, читается через
`apps.progress.services.rating_zones`.

## Принятие Положения (п. 2.1)

`GET /api/policy/` — действующая редакция и принял ли её студент.
`POST /api/policy/` — принятие. Повторный запрос второй записи не создаёт.
Профиль отдаёт флаг `policy_accepted`.

Принятие **не влияет на начисления**: по п. 2.2 они идут всем с даты
запуска, и непринятое Положение их не отменяет. Это отдельный факт, который
колледж должен уметь показать.

## Завершение сезона (п. 2.5)

```bash
dcp exec web python manage.py start_rating_year --dry-run
dcp exec web python manage.py start_rating_year
```

Рейтинг обнуляется, **неиспользованные монеты сгорают**, итог прошлого
сезона записывается в журнал.

## История начислений (п. 10.1)

`RatingLog` хранит рейтинг и монеты одной записью, с основанием, периодом
(`period_key`) и подтвердившим (`confirmed_by`). Видно в админке в журнале
рейтинга.

## Чего ещё нет

Реализованы разделы 2–9 в части начислений. Остаётся:

* **обращения студентов** (раздел 10) — маршрут куратор → тьютор и срок
  5 рабочих дней живут вне платформы; механизма подачи и учёта срока нет;
* **экран принятия Положения** во фронте — API готов, интерфейс нет;
* **признак уважительной причины** на отметке о пропуске: без него списание
  остаётся ручным;
* **архив сезона** как отдельный раздел интерфейса (п. 2.5): данные
  сохраняются в журнале, но страницы «итоги прошлого сезона» нет.

## Вопрос, который Положение не закрывает

**HikCentral в документе не упоминается ни разу.** Единственный источник
учебных данных по разделу 3 — LXP. При этом в платформе работают штрафы за
опоздания по проходам через турникеты, квесты «Утренний чек-ин», «День без
опозданий» и серии дисциплины.

Начисления этих механик рейтинга не касаются: квесты и бонусы за серии дают
только монеты. Под вопросом остаются именно **списания** за опоздания
(−3/−5/−8 рейтинга) — у них нормативного основания нет, Положение знает
единственное списание: за пропуск, 1 балл за пару.

Эти механики оставлены как есть: решение по ним за колледжем. Либо Hik
вносится в Положение отдельным пунктом, либо основанные на нём списания
отключаются — у них нет нормативного основания. Квесты при этом безопасны:
после ребаланса они начисляют только монеты, которые Положение не
регулирует.
