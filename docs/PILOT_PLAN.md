# План тестирования платформы

Пилот на группе **3ИТР2.9.24** (17 студентов, 3 курс, ИСиП). Сервер:
`186.246.2.97`. Ниже — по дням, с проверками и условиями перехода к следующему
этапу.

Сокращение, которое используется во всех командах (задавать после каждого входа
на сервер):

```bash
cd /opt/hero_path && alias dcp='docker compose -p hero_prod -f docker-compose.prod.yml --env-file .env.prod'
```

---

## Этап 0. Подготовка — 17–18 сентября

Платформа работает, студенты не заходят. Цель — закрыть то, без чего
тестирование не имеет смысла.

| Задача | Проверка готовности |
|---|---|
| Домен `hero.ithub-nalchik.ru` → A-запись на сервер | `dig +short hero.ithub-nalchik.ru` возвращает IP |
| Сертификат, `COOKIE_SECURE=1`, `SECURE_SSL_REDIRECT=1` | админка открывается по https |
| Токен LXP берётся с сервера | проверка печатает «ТОКЕН ПОЛУЧЕН» |
| Шаблоны квестов синхронизированы | `dcp exec web python manage.py sync_quest_templates` |
| Группа импортирована | `dcp exec web python manage.py squad_report itr2-24` — 17 человек |
| Telegram-алерты доходят | `dcp exec web python manage.py test_alert` |

**Не переходить дальше, пока не закрыт сертификат.** Пароли администратора и
кураторов по http ходят открытым текстом.

## Этап 1. Закрытый прогон — 21–25 сентября (пн–пт)

Студенты не знают о платформе. Проверяем, что автоматика считает по реальным
данным и считает честно.

Перед началом этапа снимите требование привязки Telegram — иначе ночные
задачи отработают вхолостую: начисления идут только привязанным, а в закрытом
прогоне не привязан никто. Вход при этом остаётся закрытым:

```bash
sed -i 's|^REQUIRE_TELEGRAM_LINK_FOR_SCORING=.*|REQUIRE_TELEGRAM_LINK_FOR_SCORING=0|' .env.prod
dcp up -d web celery celery-beat
```

**Перед открытием студентам (этап 3) верните `1`.**

Дальше платформа считает сама по расписанию: 02:00 — снимок LXP и рейтинг,
06:15 и 20:15 — проверка квестов. Утром достаточно посмотреть отчёт:

```bash
dcp exec web python manage.py squad_report itr2-24
```

Если нужно прогнать вручную, не дожидаясь ночи:

```bash
dcp exec web python manage.py pull_lxp_performance --learning-group-id 3e51acaf-990f-43bc-adf8-560f1e6e32d0 --force-rating --no-cache
dcp exec web python manage.py verify_quests
dcp exec web python manage.py squad_report itr2-24
```

Запись результата каждый день: разброс рейтинга, сколько человек без
начислений, источники.

**Понедельник 21.09.** Первый снимок только фиксирует отправную точку —
`обновлено=0`, `baselines=17`. Это не ошибка: начислять за темы, закрытые до
подключения системы, значило бы выдать рейтинг задним числом.

**Вторник 22.09.** Первый день, когда возможны начисления — по переходам тем
между снимками. Ожидаемо: у части группы появятся баллы, у части нет.

**Среда 23.09.** Смотрим, растёт ли разброс. Если у всех 17 одинаковые цифры —
автоматика не различает студентов, и это главный вывод пилота, а не сбой.

**Четверг 24.09.** Проверяем недельные квесты: посещаемость и контрольные
точки. Оба были починены после первого прогона — убеждаемся, что «100% при
нулевых занятиях» и «191/1» не вернулись.

**Пятница 25.09.** Итог недели. Разбираем каждого, у кого ноль: нет данных в
LXP, нет привязки `lxp_user_id`, или квесты не про него.

### Что считается успехом этапа

- рейтинг изменился хотя бы у половины группы;
- разброс между первым и последним больше 30 баллов;
- ни одного начисления, которое нельзя объяснить записью в журнале.

### Что считается провалом

- у всех одинаковый рейтинг — платформа не измеряет ничего;
- начисления есть у тех, кто на парах не появлялся;
- снимок LXP приходит пустым чаще, чем раз в три дня.

## Этап 2. Персонал — 28 сентября – 2 октября

Подключаем кураторов. Студенты по-прежнему не заходят. Проверяем не расчёты,
а людей: понятен ли им интерфейс без подсказок.

| День | Что делаем |
|---|---|
| Пн 28.09 | Заводим учётные записи кураторов, выдаём [руководство](Руководство_персонала.docx) |
| Вт 29.09 | Куратор сам находит очередь подтверждений и разбирает три тестовые заявки |
| Ср 30.09 | Куратор начисляет рейтинг за мероприятие через журнал |
| Чт 01.10 | Куратор выдаёт нашивку и смотрит дашборд своего отряда |
| Пт 02.10 | Собираем замечания: что искали дольше минуты, что поняли неправильно |

Тестовые заявки создаются от лица студентов группы — для этого временно
активируется один-два аккаунта.

### Успех этапа

Куратор выполняет все четыре действия **без обращения к вам**, опираясь только
на руководство.

## Этап 3. Открытие студентам — с 5 октября

Первыми пускаем ту же группу. До этого:

- бот отвечает на `/activate` и открывает вход;
- на дашборде видны квесты, магазин, отряд;
- сертификат действителен, `COOKIE_SECURE=1`.

| День | Что проверяем |
|---|---|
| Пн 05.10 | Активация: сколько из 17 дошли до входа без помощи |
| Вт 06.10 | Первые самоотчёты — заявки доходят до куратора |
| Ср 07.10 | Дуэли и респекты: вызовы создаются, ставки списываются |
| Чт 08.10 | Магазин: покупка проходит, монеты списываются, выдача понятна |
| Пт 09.10 | Итог: сколько зашли, сколько вернулись на второй день |

Главная метрика недели — **не количество начислений, а возвраты**: сколько
студентов открыли платформу повторно по своей воле.

## Что не тестируется и почему

- **HikCentral** (опоздания, посещаемость по турникету) отключён:
  портал не отдаёт данные, доступ к API у поставщика. Три недельных квеста из
  пяти в пилоте не работают — это заложено, а не сломалось.
- **YouGile** — нужен секрет вебхука; без него запросы отклоняются.
- **Нагрузка** — 17 студентов не создают нагрузки, проверять нечего.

## Постоянные проверки

Каждый день, независимо от этапа:

```bash
dcp ps                       # все контейнеры up, web healthy
curl -s https://hero.ithub-nalchik.ru/health/
dcp logs --tail 50 celery    # ночные задачи отработали без ошибок
```

Раз в неделю — что дампы базы действительно создаются:

```bash
ls -la /opt/hero_path/backups/
```

Пустой каталог означает, что при потере сервера восстанавливать будет нечего.
