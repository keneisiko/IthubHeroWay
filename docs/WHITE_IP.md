# Запуск на белом IP с обычного ПК

Инструкция для случая «сервера нет, есть домашний компьютер с белым IP».
После выполнения приложение открывается снаружи по адресу `http://ВАШ_IP/`:
интерфейс, API, админка и Swagger — всё на одном порту.

Ветка: `white_ip`. Стек: [docker-compose.white-ip.yml](../docker-compose.white-ip.yml).

> **Трафик идёт без шифрования.** Пароли от LXP при входе передаются открытым
> текстом. Это нормально для демонстрации и тестового стенда, но не для
> постоянной работы с реальными студентами. Как только появится домен —
> переходите на профиль `prod` с сертификатом, см. [DEPLOY.md](DEPLOY.md).

---

## Шаг 0. Убедиться, что IP действительно белый

Это первое, на чём всё обычно и ломается: большинство домашних тарифов выдают
адрес за NAT провайдера (CGNAT), и снаружи до вас не достучаться никаким
пробросом портов.

1. Узнайте, какой адрес видит интернет:

```bash
curl https://api.ipify.org
```

2. Зайдите в веб-интерфейс роутера и посмотрите, какой адрес он получил на
   WAN-интерфейсе (обычно «Состояние», «WAN», «Внешний IP»).

**Адреса должны совпасть.** Если на роутере адрес вида `10.x.x.x`,
`100.64.x.x` — `100.127.x.x` или `192.168.x.x`, а `ipify` показывает другой —
вы за NAT провайдера. Проброс портов не поможет: звоните провайдеру и просите
«внешний статический IP» (обычно платная услуга).

Проверка, что адрес не меняется: если провайдер выдаёт динамический белый IP,
после перезагрузки роутера адрес изменится, и `ALLOWED_HOSTS` придётся править.
Просите статический либо настраивайте DDNS.

## Шаг 1. Зафиксировать локальный адрес ПК

Роутер должен всегда пробрасывать порт на один и тот же компьютер.

Узнать текущий адрес (PowerShell):

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -notmatch 'Loopback|WSL|Docker' } | Select-Object InterfaceAlias, IPAddress
```

Запишите адрес вида `192.168.1.50`. Дальше два варианта:

* **Рекомендуемый** — в роутере в разделе DHCP найдите «Резервирование адресов»
  / «DHCP Reservation» и закрепите этот адрес за MAC-адресом вашего ПК.
* Либо задайте статический адрес в настройках сетевого адаптера Windows —
  но тогда следите, чтобы он не попал в диапазон, который раздаёт DHCP.

---

## Шаг 2. Пробросить порт на роутере

Раздел называется «Проброс портов», «Port Forwarding», «Виртуальные серверы»
или «NAT» — зависит от производителя.

| Поле | Значение |
|---|---|
| Внешний порт (WAN) | `80` |
| Внутренний порт (LAN) | `80` |
| Внутренний IP | адрес вашего ПК из шага 1, например `192.168.1.50` |
| Протокол | TCP |

**Если провайдер блокирует 80-й порт** (частая практика на домашних тарифах —
проверить можно только опытным путём), сделайте так: внешний порт `8080`,
внутренний `80`. Приложение тогда открывается как `http://ВАШ_IP:8080/`,
и этот адрес с портом нужно указать в `ALLOWED_HOSTS`.

Порты `5432` (PostgreSQL) и `6379` (Redis) **не пробрасывайте**. Стек их
наружу и не публикует — открытую базу сканеры находят за часы.

---

## Шаг 3. Разрешить порт в брандмауэре Windows

Проброс на роутере доведёт запрос до компьютера, а дальше его молча съест
брандмауэр. Откройте PowerShell **от администратора**:

```powershell
New-NetFirewallRule -DisplayName "Hero Path HTTP" -Direction Inbound -Protocol TCP -LocalPort 80 -Action Allow -Profile Any
```

Если используете другой порт — замените `80` в `-LocalPort`.

Проверить, что правило создалось:

```powershell
Get-NetFirewallRule -DisplayName "Hero Path HTTP" | Select-Object DisplayName, Enabled, Direction, Action
```

Удалить, если понадобится:

```powershell
Remove-NetFirewallRule -DisplayName "Hero Path HTTP"
```

> Профиль сети должен быть «Частная». Если Windows считает сеть общедоступной,
> часть правил не применяется. Проверить: `Get-NetConnectionProfile`.

## Шаг 4. Подготовить окружение

Нужен **Docker Desktop** с включённым Compose v2 (входит в состав).
Проверка:

```bash
docker compose version
```

Настройки Docker Desktop, на которые стоит посмотреть:

* **Settings → General → Start Docker Desktop when you sign in** — иначе после
  перезагрузки ПК стенд не поднимется.
* **Settings → Resources** — стеку нужно около 4 ГБ памяти: образ тянет
  Chromium для Playwright (сбор данных из LXP и Hik).
* **Settings → General → Use WSL 2 based engine** — оставьте включённым.

Копируем шаблон переменных:

```bash
git checkout white_ip
cp .env.white-ip.example .env.white-ip
```

Открываем `.env.white-ip` и заполняем:

| Переменная | Чем заполнить |
|---|---|
| `SECRET_KEY` | `python -c "import secrets;print(secrets.token_urlsafe(64))"` |
| `ALLOWED_HOSTS` | ваш белый IP, локальный IP, `localhost`, `127.0.0.1` — через запятую |
| `POSTGRES_PASSWORD` | любой длинный случайный пароль |
| `HTTP_PORT` | `80`, либо тот, что пробросили внутрь |
| `TELEGRAM_BOT_TOKEN` | токен бота — **без него никто не сможет активировать аккаунт** |
| `TELEGRAM_ADMIN_CHAT_ID` | ваш chat id для алертов |
| `LXP_BOT_EMAIL`, `LXP_BOT_PASSWORD` | учётка для сбора успеваемости |

Пример строки с адресами:

```env
ALLOWED_HOSTS=203.0.113.10,192.168.1.50,localhost,127.0.0.1
```

`CSRF_TRUSTED_ORIGINS` и `CORS_ALLOWED_ORIGINS` задавать не нужно: профиль
`white_ip` собирает их из `ALLOWED_HOSTS` сам. Это ровно то место, где
обычно получают «CSRF verification failed» при входе в админку.

## Шаг 5. Запуск

```bash
docker compose -f docker-compose.white-ip.yml --env-file .env.white-ip up -d --build
```

Первая сборка идёт долго — минут десять: ставится Chromium и собирается фронт.

Миграции и сбор статики выполняются автоматически при старте `web`.

Создать администратора:

```bash
docker compose -f docker-compose.white-ip.yml --env-file .env.white-ip exec web python manage.py createsuperuser
```

Наполнить данными:

```bash
alias dcw='docker compose -f docker-compose.white-ip.yml --env-file .env.white-ip'

dcw exec web python manage.py sync_quest_templates
dcw exec web python manage.py import_lxp_students --email-domain nalchik.ithub.ru
dcw exec web python manage.py backfill_lxp_user_ids --email-domain nalchik.ithub.ru
```

## Шаг 6. Проверка

Проверять нужно **в три захода** — так сразу видно, на каком участке обрыв.

**1. С самого ПК:**

```bash
curl -i http://localhost/health/
```

Ожидается `200` и `{"status":"ok"}`. Если нет — проблема в контейнерах,
смотрите `dcw logs web`.

**2. С другого устройства в той же сети** (телефон по Wi-Fi), в браузере:

```
http://192.168.1.50/
```

Если с ПК работает, а отсюда нет — дело в брандмауэре Windows (шаг 3).

**3. Снаружи** — обязательно **не** из своей сети: с мобильного интернета,
отключив Wi-Fi, либо через сервис вроде `ping.eu` / `2ip.ru/check-port`:

```
http://203.0.113.10/
```

Если два первых шага прошли, а третий нет — дело в роутере (шаг 2) или
провайдер режет порт.

> Многие роутеры не умеют «разворачивать» запрос к своему внешнему IP изнутри
> локальной сети (NAT hairpinning). Поэтому проверка снаружи по внешнему адресу
> **из дома** может не работать при полностью исправной настройке. Проверяйте
> с мобильного интернета.

## Если не работает

### Страница не открывается снаружи, но открывается с ПК

По порядку: профиль сети в Windows должен быть «Частная» → правило брандмауэра
создано (шаг 3) → проброс на роутере ведёт на актуальный локальный IP (шаг 1,
он мог смениться после перезагрузки) → адрес на WAN роутера совпадает с
`ipify` (шаг 0).

### `DisallowedHost` в логах, страница отдаёт 400

Адрес, по которому вы заходите, не перечислен в `ALLOWED_HOSTS`. Добавьте его
в `.env.white-ip` — **с портом, если заходите не на 80-й** — и перезапустите:

```bash
dcw up -d
```

### «CSRF verification failed» при входе в админку

Тот же корень: адрес не попал в `ALLOWED_HOSTS`, из которого профиль собирает
доверенные origin'ы. Проверить, что получилось:

```bash
dcw exec web python -c "from django.conf import settings; print(settings.CSRF_TRUSTED_ORIGINS)"
```

### Логин в админку принимает пароль и возвращает на форму входа

Классический симптом профиля `prod` на голом HTTP: `SESSION_COOKIE_SECURE=True`
велит браузеру не отправлять куку сессии по незашифрованному соединению.
Ошибок при этом нигде нет — просто вечная форма входа. Убедитесь, что
`DJANGO_SETTINGS_MODULE=hero_path.settings.white_ip`, а не `...prod`.

### Бесконечный редирект / `ERR_TOO_MANY_REDIRECTS`

`SECURE_SSL_REDIRECT=1` без сертификата: Django отправляет на `https://`,
там никто не слушает. В `.env.white-ip` должно быть `SECURE_SSL_REDIRECT=0`.

### Порт 80 занят

Что-то уже слушает его на ПК (часто IIS, Skype старых версий или другой
контейнер). Найти:

```powershell
Get-NetTCPConnection -LocalPort 80 -State Listen | Select-Object OwningProcess
Get-Process -Id (Get-NetTCPConnection -LocalPort 80 -State Listen).OwningProcess
```

Либо освободите порт, либо поставьте `HTTP_PORT=8080` и пробрасывайте на роутере
внешний 80 → внутренний 8080.

### Контейнер `web` перезапускается

```bash
dcw logs web | tail -50
```

Чаще всего — не заполнены `SECRET_KEY` или `ALLOWED_HOSTS`: профиль намеренно
падает на старте, а не запускается с небезопасными значениями.

### После перезагрузки ПК ничего не работает

Включите автозапуск Docker Desktop (шаг 4). У всех сервисов стоит
`restart: unless-stopped` — они поднимутся сами, как только запустится Docker.

## Эксплуатация

```bash
dcw ps                      # что запущено
dcw logs -f web             # логи бэкенда
dcw logs -f telegram-bot    # логи бота
dcw down                    # остановить (данные в томах остаются)
dcw up -d --build           # обновить после git pull
sh scripts/backup_db.sh     # дамп базы в ./backups
```

Скрипт бэкапа берёт compose-файл из переменных окружения:

```bash
COMPOSE_FILE=docker-compose.white-ip.yml ENV_FILE=.env.white-ip sh scripts/backup_db.sh
```

## Что стоит сделать дальше

1. **Домен и сертификат.** Даже бесплатный домен + Let's Encrypt закрывают
   главную проблему этой схемы — пароли открытым текстом. После этого
   переходите на `docker-compose.prod.yml`.
2. **Отдельный ПК или мини-сервер.** На рабочей машине стенд будет уходить
   в сон и перезагружаться вместе с вами.
3. **Резервные копии по расписанию** — планировщик заданий Windows на
   `scripts/backup_db.sh`.
